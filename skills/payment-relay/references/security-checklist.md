# 결제 중계 서버 보안 점검표

설계 원칙: 결제 정보는 PG 창 안에서만, 중계에는 학생 DB 없음, 내부 서버로는 **결과만 내려받기**(나가는 연결만).

## 설계 단계
| 위협 | 대책 |
|---|---|
| 엿보기·바꿔치기 | 모든 구간 HTTPS(TLS 1.2+). 내부 서버는 인증서 확인을 끄지 않는다 |
| 남이 내부 서버인 척 | 요청마다 HMAC-SHA256 서명 + 시각(5분) + 1회용 번호. 본문·주소가 한 글자만 바뀌어도 거절 |
| 바깥에서 내부 서버로 침입 | 길 없음: 포트포워딩·터널 없음, 방화벽 LocalSubnet, 중계는 내부를 못 부름 |
| 금액 위조 | 금액은 내부 서버가 정함 → 중계가 서명 → 승인 금액 대조(다르면 망취소) → 내부 반영 때 또 대조 |
| 가짜 결제 결과 | 승인은 PG와 서버끼리 다시 확인. 입금 통보는 PG가 알려 준 IP만 |
| 두 번 결제·반영 | 청구번호·거래번호 1회 처리 |
| 남의 청구서 보기 | 128비트 이상 무작위 링크(청구번호·학생 id를 주소에 넣지 않음), 기한 만료, 결제 후 즉시 닫힘, 이름 가림, 요청 횟수 제한 |
| 열쇠 유출 | PG·알림톡 키는 중계 서버 비밀 파일에만(깃헙·도커 이미지·내부 서버에 없음, 화면에 다시 안 보임). 내부 서버에는 중계 통신 키 1개(`var/`) |
| 중계 서버 털림 | 학생 DB 없음, 가린 이름·금액만 13개월, 클라우드 계정 2단계 인증 |
| 원장 관리 화면 뚫기 | 비밀번호 + 인증앱, 실패 잠금, 환불마다 재확인, 로그인·환불 즉시 원장 휴대폰 알림, 일괄 내려받기 없음 |
| 장부 불일치 | 매일 PG 거래 내역과 대조 → 다르면 원장 화면 경고 |

## 코드를 만든 뒤 꼭 보는 빈틈 (실제로 찾아 고친 것들)
1. 설정을 빠뜨리면 **모의(가짜 결제) 모드로 켜지는가** → 모드를 반드시 적게 하고, 모의 모드는 localhost에서만.
2. 테스트 결제와 실제 결제가 결과에서 구분되는가 → 결과마다 `mode`(mock/test/live), 내부 서버는 운영 중 live만 반영.
3. 가린 이름 검사가 "김철수○"·"김철수**" 같은 실명+가림을 통과하는가 → 앞 1~2글자 + 가림 + 뒤 0~2글자만.
4. 청구서 제목·항목에 전화번호가 섞일 수 있는가 → 휴대폰 번호 모양이면 거절. 환불 사유에도 학생 이름을 적지 않게 안내.
5. 접속 기록에 결제 링크 토큰(`/i/<토큰>`)이 남는가 → 앱·웹서버 접속 기록 끔(오류 기록만).
6. 예시 비밀 파일의 "(여기에 키)" 같은 안내 글이 그대로 **키로 쓰이는가** → 그런 값은 빈 값으로 보고, 키가 없으면 켜지지 않게.
7. 첫 화면이 PG 심사용 홈페이지로 쓸 만한가 → 상호·사업자 정보·약관·환불규정, 테스트 띠 없음, 키가 없으면 결제 버튼만 "준비 중".
- 고칠 때마다 테스트를 하나씩 더하고, 보고에 "자동 테스트 N → M개 통과"로 적는다.

## 남겨 두고 알리는 것 (설계상 감수)
- 본문 자체 이중 암호화는 하지 않음(내용이 가린 이름·금액뿐, HTTPS에 기댐).
- 관리자 로그인 실패 잠금은 남이 일부러 틀려 잠글 수 있음.
- 중계 응답에는 별도 서명 없음(HTTPS 인증서 확인에 기댐).

## 점검 방법
- 휴대폰 LTE로 내부 관리 주소 → **안 열려야 정상**. 게스트 와이파이에서도 안 열림.
- 중계 주소는 결제 화면 외 경로가 막혀 있는지.
- 서명 위조·만료·재사용 요청이 거절되는지 테스트로.
